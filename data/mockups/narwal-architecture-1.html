Architecture

Narwal lives next to Hashtopolis in the same dev container but doesn't fork it. The bridge talks to upstream's REST API, so upstream updates don't carry diffs. Simulation uses hashcat --stdout for fast interactive feedback; PCFG/OMEN run async for the headline guess-number curves.

[ Hashtopolis devcontainer ] ├─ Narwal web UI ──▶ FastAPI backend ──▶ Hashtopolis bridge │ single-page · vanilla JS plan = compose(target, refs, cluster) REST · preview JSON │ └─ tools: demeuk · hashcat --stdout · umap-learn · PCFG/OMEN · datasketch
Sidecar over fork. Upstream Hashtopolis moves; our diffs don't have to. If something belongs upstream, we send a PR.

Glossary

household-day
How Narwal reports savings — one number, one unit. Each plan is translated into household-days: the electricity an average Dutch home consumes in 24 hours (≈10 kWh). One full day on the cluster ≈ 9 household-days; a clever 2-hour plan can save ~0.7 household-days.
cluster
Default reference rig in the planner. 8× RTX 4090 ≈ 3.6 kW sustained → ≈ 86 kWh per cluster-day.
plan-only
Narwal never attempts the user's target hashes itself. Simulation runs against the reference corpora; Hashtopolis cracks the real target.
