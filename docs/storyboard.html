Scene 1 — Setup & dataset selection

Three rails: pick reference datasets to compare against, upload the target hashlist (plan-only by default), set the cluster spec that drives every runtime estimate downstream.

Scene 2 — The attack composer

Drag attacks from the library into the pipeline, toggle blocks on/off, watch the budget meter and downstream curves recompute. Each block shows the expected residual hit rate after preceding attacks have already removed their share.

Scene 3 — Cumulative mask coverage headline

Van Heijningen 2013 Appendix O.2, rendered live. Bars stack cumulative % cracked as masks are added in efficiency order. Dashed line on the right axis is cumulative cracking time on the 8× RTX 5080 cluster — the bend marks the natural budget kink.

RockYou cum % · 14.3M 000webhost cum % · 15M cracking time (min)
RockYou cumulative reaches 67.19% at mask 25 — straight from Van Heijningen Table O.1. The first 19 masks crack ~57% of passwords in under 4 minutes on this cluster; the last six masks add only ~10% but cost most of the cumulative time.

Scene 3b — Per-position frequency heatmap

Van Heijningen Figure 5 / Appendix T. Each cell is the percentage of passwords with character c at position p. Toggle datasets to see the dataset's character at a glance: vowels in early slots = natural-language, all-digits column = PIN-style (Taobao), shifted patterns = Cyrillic-keyboard (Mail.ru).

Scene 5 — Dataset similarity cluster

UMAP projection of reference corpora. Distance ≈ password-distribution divergence; bubble size ≈ √cardinality. Three natural clusters: consumer leaks, corporate, high-entropy outliers. The MAYA RQ6 analog, operationalised for "where does my target land?"

Scene 6 — Verdict & recommendation

The actual product output. Plain-English strongest/weakest, plus a recommended attack chain with per-step budget allocation, keyed to whichever cluster the target landed in on Scene 5. One button ships it to Hashtopolis.

Scene 7 — Architecture (Hashtopolis sidecar)

Narwal lives alongside Hashtopolis in the same dev container but doesn't fork it. The bridge talks to upstream Hashtopolis's REST API, so upstream updates don't carry diffs. Simulation uses hashcat-stdout for fast interactive feedback; PCFG/OMEN run async for the headline guess-number curves.
